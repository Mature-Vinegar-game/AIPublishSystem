## 1 业务场景与方向

### 1.1 一句话场景

印制业务员接到一本 16 开、3000 册、四色（彩色页 4）、胶装的图书印制需求后，在系统里录入印数与规格参数，由 AI Agent **自主调用报价检索、规则校验、成本计算三类工具**，产出一份逐项可复算的印制成本测算单；测算单经逐条依据核对、人工修改、提交审核后由审核员通过或退回，全过程留痕、至少两个版本可查。

- 业务方向：任务书"印制参数校验与成本测算" [原文 L20]（4 大类中的**印制**类），本组只做这一项，不覆盖出版全流程 [原文 L3]。
- 使用对象：出版社印制岗业务员与成本审核岗；数据为**教学模拟数据**，用于演示与验收，不代表真实报价 [原文 L61]。
- 解决的问题：把"查报价单 → 按规则核参数 → 手算五项成本 → 主管复核"这条纸质/Excel 链路，做成**可追溯依据、可复算、可审核**的单体 Web 系统。

### 1.2 业务痛点与系统对策

| 痛点（真实印制场景） | 本系统对策 | 对应必做功能 |
|---|---|---|
| 报价散落在 Excel/纸质报价单，查一次要翻多个文件 | 资料库统一存纸张/工艺/装订/费率报价，工具按关键词检索并返回 `material_no` | 资料与数据管理 [表2 L29] |
| 印数、印张、开本、装订方式之间互相约束，靠人记 | `rules` 表存 ≥10 条规格规则，`validate_spec` 工具按规则校验并返回 `issues[].rule_code` | AI 业务结果 [表2 L30] |
| 五项费用口径不一，换个人算出不同结果 | 成本公式唯一口径（§4.3），每个 `line_item` 带 `formula` 文本，可手工复算 | AI 结果一致 [表6 L90] |
| 出了错无法追责，改过的版本找不到 | `ai_results`→`result_versions`（AI/MANUAL 两类来源）→`review_records`，版本只增不改 | 人工确认与版本 [表2 L32] |
| 主管不信"模型算的" | 依据三跳：结果依据 → 资料/规则详情 → 该次工具执行记录 | Agent 执行记录 [表2 L31] |

### 1.3 使用边界

- 只处理**表单录入**的印制参数与**库内**报价/规则数据；输入格式限表单/JSON（资料录入为 JSON 文本域），不解析 PDF、不做 OCR [原文 L37]。
- 计算结果为**教学演示口径**，不接入印厂真实报价系统、不对接设备与订单 [原文 L3]。
- 导入的资料内容只能作为"数据"，其中若出现"忽略权限/你是管理员"等文字，**不改变任何权限判定** [原文 L61]。

## 2 角色与权限

### 2.1 两类角色

按场景命名，与登录账号、后端校验一致 [表2 L27][原文 L35]：

| 角色码 | 场景名称 | 演示账号 | 职责 | 主要权限 |
|---|---|---|---|---|
| `operator` | 印制业务操作员 | `operator/123456`（张伟） | 建任务、录参数、跑 AI 测算、改结果、提交审核 | 本人任务全流程；资料/规则新增；不可审核 |
| `reviewer` | 印制成本审核员 | `reviewer/123456`（李静） | 复核测算依据与金额，通过或退回 | 待审/已审任务只读 + 审核动作；**不可建任务、不可运行 AI**【设计】 |

- 密码 `pbkdf2_hmac('sha256', pwd, salt, 100000)` 十六进制存储，不存明文 [原文 L78]；登录签发 HMAC-SHA256 cookie（`uid|role|exp|sig`，有效期 12h）。
- 角色不可在前端"扮演"切换，必须两个账号分别登录 [表2 L27]。

### 2.2 权限矩阵（接口级，后端强制）

| 能力 / 接口 | operator | reviewer | 后端拒绝口径 |
|---|---|---|---|
| 登录、查看本人信息（`/auth/login`、`/auth/me`） | ✔ | ✔ | 未登录 401 |
| 新建任务（`POST /business-tasks`） | ✔ | ✘ | 403 |
| 修改任务（`PUT /business-tasks/{id}`） | 仅本人、仅 `PENDING/REJECTED` | ✘ | 非本人 404；状态不符 409 |
| 关联资料（`POST /business-tasks/{id}/materials`） | 仅本人 | ✘ | 404/403 |
| 保存人工版本（`POST /business-tasks/{id}/results`） | 仅本人、仅 `PENDING/REJECTED` | ✘ | 409（已提交/已通过冻结） |
| 运行 AI（`POST /business-tasks/{id}/ai-tasks`） | 仅本人 | ✘ | 403/409/429 |
| 提交审核（`POST /business-tasks/{id}/submit`） | 仅本人、仅 `PENDING/REJECTED` | ✘ | 409（状态冲突）；依据不一致 → 409 `BASIS_MISMATCH` |
| 审核（`POST /business-tasks/{id}/review`） | ✘ | ✔（仅 `PENDING_REVIEW`） | 403/409 |
| 查任务/结果/版本/执行记录 | 仅本人 | 仅待审/已审范围 | 404（对象不属于本人/不在审核范围） |
| 资料库、规则库查询 | ✔ | ✔ | 401 |
| 新增资料/规则 | ✔ | ✘ | 403 |

> 统一口径：**401 未登录**、**403 角色不足**、**404 对象不属于本人或不在审核范围**（用 404 而非 403，避免泄露对象存在性）、**409 状态冲突/重复提交/版本冻结** [原文 L27]。管理员类操作一律走业务接口，不允许改库改状态。

### 2.3 6 个越权拒绝点（现场可逐条验证）

1. operator 调审核接口 → 403，返回明确错误文案。
2. reviewer 调新建/修改任务、运行 AI → 403。
3. operator 用他人 `task_id` 查详情/版本/结果/执行记录 → 404，不返回任何数据。
4. 未登录或 cookie 过期访问任意 `/api/*` → 401。
5. 前端隐藏的按钮直接构造请求 → 与 2/3 同口径被拒。
6. 资料内容含"忽略权限"等指令 → 权限判定不变 [原文 L61]。

## 3 主流程：7 个环节

流程固定为任务书 7 个环节，不增不减 [原文 L23]；每环节都有落点页面/接口，演示与文档同源。

### 3.1 7 环节 → 页面 → 接口 → 证据

| # | 环节 [原文 L23] | 用户动作（点击级） | 页面（BUILD_SPEC §7） | 主要接口 | 落库/证据 |
|---|---|---|---|---|---|
| 1 | 创建任务 | 任务列表页点"新建任务" → 填 `title`/`goal` → 保存 | `tasks.html` → `task_new.html` | `POST /api/business-tasks` | `business_tasks`（`task_no`、`revision=1`、`status=PENDING`） |
| 2 | 填写需求或导入数据 | 在表单填 `format`/`print_sheet`/`qty`/`paper_type`/`binding`/`color_pages`/`process`；在任务详情"关联资料"选纸张报价与规则 | `task_new.html`、`task_detail.html`、`materials.html` | `PUT /api/business-tasks/{id}`、`POST /api/business-tasks/{id}/materials` | `business_tasks.params_json`、`task_materials` |
| 3 | 调用工具处理 | 任务详情点"运行 AI 测算" → 轮询状态徽标 | `task_detail.html` + `app.js`（2s 轮询） | `POST /api/business-tasks/{id}/ai-tasks`（202）→ `GET /api/ai-tasks/{id}` | `ai_tasks`、`tool_call_records`（同一 `business_task_id`） |

| 5 | 人工修改或确认 | 改金额/说明后"保存人工版本"，填写变更说明 | `task_detail.html` 版本区 | `POST /api/business-tasks/{id}/results` | `result_versions`（`source=MANUAL`，`version_no` 递增） |
| 6 | 审核 | operator 提交 → reviewer 在审核区"通过"或"退回+意见" | `task_detail.html` 审核区（reviewer 可见） | `POST /api/business-tasks/{id}/submit`、`POST /api/business-tasks/{id}/review` | `business_tasks.status`、`review_records`（`action`/`opinion`/`reviewer_id`） |
| 7 | 查询历史记录 | 任务列表按状态筛选；任务详情版本列表切换 v1/v2；重进任务看结果与执行记录 | `tasks.html`、`task_detail.html` | `GET /api/business-tasks`、`GET /api/business-tasks/{id}`、`GET /api/business-tasks/{id}/versions` | 全部记录按 `business_task_id` 可回查（同一任务 ID 贯穿 [原文 L49]） |

### 3.2 状态机

**业务任务四态** [原文 L35]：

```
PENDING（待处理） --提交审核--> PENDING_REVIEW（待审核）
PENDING_REVIEW --审核退回（意见必填）--> REJECTED（退回）
REJECTED --修改后重新提交--> PENDING_REVIEW
PENDING_REVIEW --审核通过--> COMPLETED（完成，只读）
```

- `PENDING/REJECTED` 才允许改参数、跑 AI、保存人工版本；`PENDING_REVIEW/COMPLETED` 版本冻结，改 → 409【设计】。
- 退回意见必填；完成态仅可查看与查版本 [表2 L32]。

**AI 任务四态** [原文 L35]：`PENDING → RUNNING → SUCCEEDED | FAILED`；失败可"重试"生成**新** `ai_tasks` 记录（旧记录保留），受 `MAX_AI_RUNS=10` 限制（超限 429）[原文 L49]。进程启动时把残留 `RUNNING` 清理为 `FAILED(STALE_RUNNING)`，杜绝永久运行中。

## 4 核心参数与成本口径

### 4.1 任务参数（`business_tasks.params_json`）

下表共 11 个表单字段：`title`/`goal` 落 `business_tasks` 列，其余 9 项落 `params_json`。表单标 `*` 的必填 6 项为 `title/goal/print_sheet/qty/paper_type/binding`；`format` 表单可空，但 `validate_spec` 视为必填（缺 → `SPEC-REQUIRED`）。

| 参数 | 中文 | 必填 | 取值/类型 | 校验规则（`validate_spec`，规则来自 `rules.rule_type=spec`） |
|---|---|---|---|---|
| `title` | 任务名称 | ✔ | 字符串 ≤100 | 非空；为空 400 指字段 |
| `goal` | 业务目标 | ✔ | 字符串 ≤500 | 非空 |
| `book_title` | 书名 | ✘ | 字符串 | 仅展示，不参与计算 |
| `format` | 开本 | ✔（规则校验） | 枚举 `16开/32开/大32开` | 白名单外或为空 → `issues[]` 含 `RULE-FMT-001`；表单不标 `*` |
| `print_sheet` | 印张 | ✔ | 数值 | `>0` 且 `≤50` |
| `qty` | 印数 | ✔ | 整数 | `≥500` 且为整数 |
| `paper_type` | 纸张 | ✔ | 字符串 | 非空，且能在 `materials(type=paper)` 找到 |
| `binding` | 装订 | ✔ | 枚举 `胶装/骑马订/精装` | 枚举外 → 规则命中；并与印张匹配校验 |
| `color_pages` | 彩色页数 | ✘ | 整数 0-4 | `≥0`；`>0` 视为四色档，`=0` 单色档 |
| `process` | 工艺 | ✘ | `无/覆膜/UV/烫金` | 可空；选"无"则工艺费=0 |
| `note` | 备注 | ✘ | 字符串 | — |

前端做字段级必填/范围提示；后端在创建/更新时校验 `title`/`goal` 非空与参数类型，不合法返回 400 + 具体字段文案；参数的业务范围、枚举白名单与资料存在性由 `validate_spec` 在运行期校验，返回 `issues[{field,message,rule_code}]`（规则码如 `SPEC-QTY-MIN`、`MATERIAL-PAPER-NOT-FOUND`，或 `rules` 表中的 `rule_code`）[表2 L28]。

### 4.2 Agent 可用工具（4 个，3 类）

| 工具 | 类型 | 入参 | 返回 | 失败口径 |
|---|---|---|---|---|
| `search_quotes` | retrieval | `keyword?`(≤50)、`category?∈paper/process/binding/rate` | `items[{material_no,title,type,source,version_no,content}]` | 无结果 `DATA_NOT_FOUND` |
| `get_rules` | retrieval | `business_type?`（默认 `print_cost`） | `rules[{rule_code,name,rule_type,severity,content}]` | 空规则集 `DATA_NOT_FOUND` |
| `validate_spec` | validation | `params{}` | `valid`、`issues[{field,message,rule_code?}]`、`normalized{}` | 参数非法 `TOOL_ARGS_INVALID` |
| `calculate_cost` | calculation | `params{}` | `line_items[{name,formula,amount}]`、`total`、`per_copy`、`currency`、`missing[]` | 缺单价 `DATA_NOT_FOUND` + `data.missing[]` |

统一返回信封：`{ok, data, source:{ids:[...]}, warnings:[], error_code?, error_message?}`；**每个结果必须带 `source.ids`**（`material_no`/`rule_code`），这是依据校验与"依据三跳"的锚点 [表3 L46][原文 L49]。成功测算需覆盖 ≥2 类工具（retrieval/validation/calculation）且每类 ≥1 次成功，否则判 `NO_TOOL_CALL` [原文 L48]。

### 4.3 成本公式（全项目唯一口径，与 `calculate_cost` 实现一致）

设：印数 `Q`、印张 `S`、色数档 `C`（`color_pages>0?4:1`）、纸张单价 `P_paper`（元/令）、单色千印张价 `P_print`（元/千印张/色）、装订单价 `P_bind`（元/千册）、工艺单价 `P_proc`（元/千册）。

| # | 项目 | 公式 | 说明 |
|---|---|---|---|
| 1 | 用纸量（令） | `ceil(Q × S ÷ 1000 × 1.05)` | 1.05 为损耗系数；向上取整到整令 |
| 2 | 纸张费 | `用纸量 × P_paper` | `P_paper` 取 `materials(type=paper).content.price_per_ream` |
| 3 | 印刷费 | `Q ÷ 1000 × S × P_print × C` | `P_print` 取 `materials(type=rate).content.price_per_1000_sheets_per_color` |
| 4 | 制版费 | `C × 80` | 80 元/色为演示参数，来源 `rate` 资料 |
| 5 | 装订费 | `Q ÷ 1000 × P_bind` | 取 `materials(type=binding).content.price_per_1000` |
| 6 | 工艺费 | `Q ÷ 1000 × P_proc` | 取 `materials(type=process).content.price_per_1000`；无工艺 = 0 |
| 7 | 总成本 / 单册 | `total = ②+③+④+⑤+⑥`；`per_copy = round(total ÷ Q, 2)` | 货币 `CNY`；缺任一必需单价 → `ok=false, DATA_NOT_FOUND`，`data.missing[]` 列出缺项，**不输出 total** |

**算例（16 开 / 3000 册 / 印张 12 / 四色（`color_pages=4`）/ 胶装 / 覆膜，取种子报价）**

| 项目 | 计算式（即 `line_item.formula`） | 金额 |
|---|---|---|
| 用纸量 | `ceil(3000×12÷1000×1.05)=38` 令 | — |
| 纸张费 | `38×265=10070.00`（纸张单价 265 元/令） | 10070.00 |
| 印刷费 | `3000÷1000×12×22×4=3168.00`（22 元/千印张/色 × 4 色档） | 3168.00 |
| 制版费 | `4×80=320.00` | 320.00 |
| 装订费 | `3000÷1000×180=540.00`（胶装 180 元/千册） | 540.00 |
| 工艺费 | `3000÷1000×180=540.00`（覆膜 180 元/千册） | 540.00 |
| **总成本** | `10070+3168+320+540+540` | **14638.00** |
| **单册成本** | `14638÷3000≈4.8793` → 2 位 | **4.88** |

> 该算例同时是 [06 测试用例](./06_测试用例.md) TC11 的复算基准；数值随换纸张/换印数变化，现场可当场重算。

### 4.4 依据三跳（"凭什么这个结果对"的答法）

1. **第 1 跳**：结果页"依据"列表 → `basis_refs[]{type:'material'|'rule'|'calc', id, label}`；
2. **第 2 跳**：点 `material_no`/`rule_code` → 资料库/规则库详情（含来源 `source`、版本 `version_no`）；
3. **第 3 跳**：执行记录中该次工具调用的 `args_json` 与 `source_ids_json` → 证明"这次跑的就是这条数据"。

校验口径：`basis_refs.id` 必须属于本次工具 `source.ids` ∪ 任务关联资料 `material_no` ∪ `rule_code` ∪ 参数业务数据；不命中则 `basis_ok=false` 并追记 `uncertain_items`（不判失败）；库内已不存在的 id → 软标记"依据已变更"；**数据不足仍输出 total** → 重试 1 次仍犯则 `FAILED(DATA_FABRICATED)`【设计，对齐 BUILD_SPEC §6】。

### 4.5 运行限额（页脚常驻展示）

| 限额 | 值 | 作用 |
|---|---|---|
| `MAX_TOOL_CALLS` | 10 次/任务 | 防无限工具调用 |
| `MAX_LLM_ROUNDS` | 8 轮/任务 | 防模型往返死循环 |
| `LLM_TIMEOUT_S` | 30 s/次 | 单次模型请求超时 |
| `TOOL_TIMEOUT_MS` | 3000 ms/次 | 单次工具执行超时 |
| `AI_RUN_TIMEOUT_S` | 120 s/任务 | 整体运行超时（前端轮询 120s 提示） |
| `MAX_AI_RUNS` | 10 次/任务 | 重试上限，超限 429 |

## 5 系统设计

### 5.1 数据模型（10 张表，详见 [05 数据字典](./05_数据字典.md)）

| 表 | 作用 | 关键字段（ID 链路） |
|---|---|---|
| `users` | 账号与角色 | `id`、`role_code ∈ operator / reviewer` |
| `business_tasks` | 业务任务与参数 | `id`、`task_no`、`params_json`、`status`、`revision`、`created_by` |
| `materials` | 纸张/工艺/装订/费率/书目资料 | `id`、`material_no`、`type`、`source`、`version_no`、`content_json` |
| `task_materials` | 任务↔资料关联 | `task_id`、`material_id`、`link_role` |
| `rules` | 规格/成本规则 | `id`、`rule_code`、`rule_type`、`severity`、`content_json` |
| `ai_tasks` | AI 运行实例 | `id`、`business_task_id`、`status`、`input_snapshot_json`、`counters_json`、`error_code` |
| `tool_call_records` | 每次工具调用一条 | `ai_task_id`、`business_task_id`、`seq`、`tool_name`、`args_json`、`source_ids_json`、`status`、`latency_ms` |
| `ai_results` | AI 产出与依据 | `ai_task_id`、`business_task_id`、`content_md`、`structured_json`、`basis_refs_json`、`basis_ok` |
| `result_versions` | 可查版本（AI/MANUAL） | `business_task_id`、`version_no`、`source`、`content_md`、`change_note` |
| `review_records` | 审核流水 | `business_task_id`、`version_id`、`action ∈ APPROVE / REJECT`、`opinion`、`reviewer_id` |

关系要点：`business_tasks` 是**唯一主线**，`task_materials / ai_tasks / ai_results / result_versions / review_records` 全部带 `business_task_id`；`tool_call_records` 同时带 `ai_task_id` 与 `business_task_id`，因此"结果→调用→任务"可互跳 [原文 L31][原文 L49]。版本只增不改，`UNIQUE(business_task_id, version_no)`。

### 5.2 接口设计（24 个 REST，统一 `/api` 前缀）

| 分组 | 接口 | 数量 |
|---|---|---|
| 认证 | `POST /auth/login`、`GET /auth/me` | 2 |
| 业务任务 | `POST /business-tasks`、`GET /business-tasks`、`GET /business-tasks/{id}`、`PUT /business-tasks/{id}`、`POST /business-tasks/{id}/materials`、`POST /business-tasks/{id}/results`、`GET /business-tasks/{id}/versions`、`POST /business-tasks/{id}/submit`、`POST /business-tasks/{id}/review` | 9 |

### 5.3 模型与 Agent 设计

- **接入方式**：`httpx` 直连 `${LLM_BASE_URL}/chat/completions`（OpenAI 兼容），`Authorization: Bearer ${LLM_API_KEY}`；请求带 4 个工具的 JSON Schema、`tool_choice="auto"`、`temperature=0.2`。
- **为什么不是"写死流程"**：工具名与参数由模型在每轮自行选择，后端只做参数校验、执行与回填；同一任务内要求 ≥2 类工具连续调用 [原文 L48]。
- **工具消息协议**：每个 `tool_call` 必须回填一条 `role=tool` + `tool_call_id` 的消息，否则模型侧协议不闭合【设计，对齐 OpenAI 工具调用规范】。
- **完成判定护栏**：≥2 类工具各 ≥1 次成功、`basis_refs` 非空、JSON 解析成功；不满足回填提示重试（≤1~2 次），仍不满足判 `NO_TOOL_CALL`/`DATA_FABRICATED`【设计】。
- **异步与幂等**：`POST /ai-tasks` 写 `PENDING` 后交后台线程（`threading.Thread(daemon=True)`）执行并立即 202；前端 2s 轮询；重复启动受任务状态与 `MAX_AI_RUNS` 约束。
- **真实/模拟双模**：`LLM_MODE=real|mock`，`GET /api/system/meta` 返回 `llm_mode`、`model`、`key_configured`；页面与结果标注 `model_mode`。**验收固定 real**，mock 仅用于无 key 开发且必须标注 [原文 L63]。
- **限额**见 §4.5；`ai_tasks.counters_json` 记录 `rounds/tool_calls/distinct_types/model_calls`，页脚常驻展示 [原文 L49]。
